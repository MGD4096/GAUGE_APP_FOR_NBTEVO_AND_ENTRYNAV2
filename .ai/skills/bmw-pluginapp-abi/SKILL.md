# Talking to the PluginApp framework without headers

There are no BMW headers. Every framework class is declared by hand in `src/bmw_framework.hpp` so that the
compiler produces **exactly** the mangled names the car exports, and every object layout is what the car's code expects. A
mismatch does not fail the build (`--allow-shlib-undefined`); it fails at `dlopen` in the car, or corrupts memory.

## Adding a framework call

1. Find the exact signature in **both** libraries:
   ```sh
   nm -D --defined-only lib/Entry_Evo_libs/libAppFramework.A.so | c++filt | grep 'PluginApp::triggerEvent'
   nm -D --defined-only lib/NBT_evo_libs/libAppFramework.A.so   | c++filt | grep 'PluginApp::triggerEvent'
   ```
   If it is missing from either, do not use it.
2. Declare it with the same parameter types, `const` and references (`unsigned` vs `unsigned int` is the same;
   `int` vs `unsigned`, or `const T&` vs `T`, is not). Check the mangled name too:
   `nm -D ... | grep _ZN3bmw9PluginApp12triggerEventEj`.
3. Add the same declaration and a recording implementation to `tests/fake_appframework.*`, then a check in
   `tests/app_host_test.cpp`. The host test loads the plugin with `RTLD_NOW`, so a declaration the fake lacks (or
   spells differently) fails there.
4. Note next to the declaration whether it is car-verified, and by whom (GaugeApp, entry-aad, NbtAad).
5. `make check` runs `tests/check_abi.sh`: every `_ZN3bmw…` import of the plugin must be exported by
   `lib/Entry_Evo_libs` **and** `lib/NBT_evo_libs` (skipped with a note when a folder lacks the libraries).

Prefer calls already proven on the car by GaugeApp or the sibling projects (`../EntryEvo-Android-Auto`,
`../Supra-iDrive6-Android-Auto`) over new ones; copy their XML element shapes rather than inventing attributes.

## Objects whose layout we fake

- **`PluginApp`**: constructed by placement `new` into at least `kPluginAppStorage` (0x200) zeroed bytes. Never
  `sizeof(bmw::PluginApp)` from our own declaration: it is a guess, the storage constant is the contract.
- **Our overrides** go through a copy of the vtable (34 slots: onError 21, onInit 22, onFinalize 23). The override
  calls the base implementation explicitly (`self->onInit()`), and handlers are registered **before** the base
  `onInit`.
- **Runnable stand-in**: a 5-word vtable copied from `_ZTVN3bmw8RunnableE` (offset-to-top, typeinfo, two destructors,
  `run`), destructors are no-ops because the objects are static. A posted Runnable must stay alive until it runs:
  never post a stack object.
- **`bmw::Image`** has no exported destructor: destroy `BufferStream` (+4) and `BasicString<char>` (+0) by hand, in
  reverse order of construction. Assert the storage size.
- **Delegates** are `{ void* object; R (*stub)(void*, A1) }`. CDS gives no property name to the callback, so each
  subscription needs its own stub (template `onCds<P>`); keep the stub table and the enum the same length (assert it).

## Lifecycle rules

- `create` may return `NULL` (off switch, crash guard): iDrive then starts without the app. Keep that path cheap and
  logged.
- `onFinalize` sets the global app pointer to `NULL` first; every posted Runnable checks it and stops re-posting.
  Then persist state, then call the base `onFinalize`.
- Subscribe to CDS ~1.5 s after `onInit` (posted), not inside it. Never call `cdsSetPropertyAsync` (writes to the
  car).
- Callbacks return `true` and return fast; do not re-enter the framework from inside a callback beyond `updateModel`
  / `triggerEvent`.

## The XML contract (`GaugeApp.xml`, generated by `make_db.py`)

- All ids (models, components, actions, events, states) are unique in the whole file; generate them from named
  constants and export the ones C++ needs into `src/gauge_ids.hpp`. C++ never hard-codes an XML id.
- Child states (`parentId`) also show the parent's OPTION entries: put shared entries only in the parent.
- An entry button with a `raAction` (not an `hmiAction`) lets the app choose the state with a `focusEvent` +
  `triggerEvent`. It also means the button is dead if the app's handler is not registered.
- Text DB: ASCII only. Image DB: tiny (a large one made the EntryNav2 HMI show no picture, onError 9). Pictures go as
  data into `raImageModel`s.
- About 60 images per state: `make_db.py` (`check_xml`) fails when a state goes over, and also on a duplicate id or
  a reference (`action`, `model`, `target`, `parentId`) that points nowhere.
- XML comments must not contain `--` (strict parsers reject the file; HmiMain3D happened to accept it).

## Debugging on the car

- The log (`/var/local/data/GaugeApp/gauge-app.log` on EntryNav2) records create / onInit / onError and every
  entry and setting action: read it before guessing.
- `onError <n>` right after loading usually means the XML or DBs were rejected; diff the XML against the last
  version that worked.
- A dead button: check that the action id in the XML equals the one passed to `addHandler`, and that it is registered
  before the base `onInit`.

## Where GaugeApp differs today

- The fake (`tests/fake_appframework.hpp`) declares the same classes with its own layout (it plays the library:
  virtual slots, recorded calls), so it cannot share `bmw_framework.hpp`. Drift is caught by `RTLD_NOW` in the host
  test (fake vs plugin) and by `check_abi.sh` (plugin vs the cars), not by the compiler.
- NBT Evo: nothing has run on hardware. Treat every NBT-specific path as unverified.
